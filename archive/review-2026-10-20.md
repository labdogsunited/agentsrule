# GPU review and language assessment — 2026-10-20

**Status:** both code findings are fixed, and regression tests are in `crates/emerge-gpu/tests/limits.rs` (see "Limits found by review" in [gpu-runtime.md](../proposals/gpu-runtime.md)). The stale catalyst note in `DISCREPANCIES.md` is corrected. Next steps 2 to 5 are still open, in [plan-next.md](../proposals/plan-next.md).

This document records the review of commits `00ede0c` and `49ecb88`, followed by my assessment of `.em` at `49ecb887faad93b3149ebc5afe7dfe3f6228b668`. “The ideas we were scouting” means the design and research proposals checked into this repository. This is an assessment of their adoption, not a new review of the external literature.

**My assessment:** `.em` is becoming a credible, inspectable language for resource-constrained evolutionary experiments. Much of the original creatures model now executes, and several of the most practical scouting ideas have become tools. The larger ambition—a general graph language in which creatures are an ordinary library application—remains a design. The recent GPU work substantially improves the execution foundation, but it does not close that language gap.

**Code review: two confirmed findings.**

| Priority | Finding | Location |
| :-- | :-- | :-- |
| P1 | Oversized request buckets can silently corrupt arbitration and exceed store caps. | [`bucket_sort`, move.wgsl](../crates/emerge-gpu/src/move.wgsl), lines 789–792; error check in [`resident.rs`](../crates/emerge-gpu/src/resident.rs), lines 662–670 |
| P2 | A world with more than 64 reaction laws crashes when copying its law index. | [`resident.rs`](../crates/emerge-gpu/src/resident.rs), lines 288 and 442–444 |

The first issue comes from the bucket-sort path introduced in `00ede0c`. Requests with the same store/substance key always land in the same bucket. If a bucket has more than 256 entries, `bucket_sort` sets an error word and returns without writing its sorted segment. Subsequent `share` and commit dispatches still execute, using a list that is not correctly grouped and ordered.

Increasing the bucket count cannot solve a single key with more than 256 requests. This is possible in an ordinary dense population competing for one cell's substance, as well as with many world inflows. Other keys colliding in the same bucket can also exceed its capacity.

The error check added in `49ecb88` does not reliably stop this path. It runs only when children were born and the tick is divisible by eight. A run with no births can continue indefinitely without checking the error. With auditing enabled, clearing the flow buffer can erase the flag before a later check.

**Observed reproduction:** a one-cell world with 600 alternating inflow laws—300 each for carbon and nitrate, requesting 20,000 micro-units per law—diverged after one tick without reporting the overflow. CPU cell amounts were 1,999,000 carbon and 2,000,000 nitrate; the GPU produced 312,049,000 and 314,840,000 respectively. The carbon amount includes the surviving entity's take. The GPU values exceeded the cell capacities.

Fix this before relying on the optimized path for arbitrary supported worlds. Prefer a correct fallback for oversized buckets. At minimum, prevent arbitration and commitment from proceeding after an overflow, and report the error independently of births and audit settings. Add regression coverage for one heavily contested key and for distinct keys that collide in a bucket.

The second issue comes from replacing host parameter writes with recorded buffer copies. `consts` contains exactly the integers `0..64`, but Transform loops over all `P_NRLAWS` reaction laws. At law index 64, the four-byte copy starts at byte offset 256, beyond the source buffer.

**Observed reproduction:** a world with 65 copies of a valid `Law::React` failed with:

```text
Copy at offset 256 for 4 bytes would end up overrunning
the bounds of the Source buffer of size 256
```

The previous host-write approach did not impose this limit. Allocate enough index words for the actual reaction-law count, retaining any minimum needed by other parameter copies, or encode these values through another ordered mechanism.

**Validation and limits of the review.** Both findings were reproduced using llvmpipe with `EMERGE_GPU_POOL_WORDS=1048576`. A temporary harness compiled the reference dish with one `Drifter`, mutation disabled and contract mode enabled, reduced the grid to one cell, reset the entity's position and cell, and replaced the world laws. It compared one complete GPU tick with the CPU using `compare_full`. Control cases with 64 reaction laws and 200 alternating inflows passed. These results establish the failures on that backend; they do not establish general floating-point parity across drivers.

The crate compiled successfully. The full `cargo test -p emerge-gpu --no-fail-fast` run was interrupted before completion; it was not a passing regression run. The temporary harness was removed, and the reviewed implementation was left unchanged. Longer audits and performance results cited elsewhere in this document are repository records, not experiments rerun for this assessment.

**What I think is working in the language.**

The strongest design choice is giving evolution a world with explicit resource rules. Genomes control behavior, but transfers, inventories, costs, reaction balance and dissipation constrain what that behavior can accomplish. Mutation cannot simply invent a source of energy. This makes failures worth investigating: an apparently useful genome can fail because it cannot pay before acting, cannot acquire an input, or cannot retain a product.

The fixed tick schedule is also valuable. Snapshot reads, sequential reactions, transfer arbitration and newborn timing make the model explainable in small examples. There is a learning cost because source declaration order does not expose the whole schedule. The response so far has been sensible: document the schedule, test it, and expose `emerge order`. The [prediction pilot](../proposals/prediction-pilot/README.md) recorded improved answers after the runtime rules were added to the language reference. That is encouraging evidence for legibility, although the small pilot is not a general authoring benchmark.

The authoring changes are well chosen. Constants, lineage `extends`, explicit placement after labels, patches and an expanded view let an experiment express its actual difference from a baseline. Their value is larger than saving typing: they make accidental experimental changes easier to see. The equivalence tests for [constants](../crates/emerge-ref/tests/consts.rs), [inheritance](../crates/emerge-ref/tests/extends.rs) and [world variants](../crates/emerge-ref/tests/variants.rs) support that claim.

The CPU/GPU comparison work is a further strength. Comparing whole states and mutations gives the project a way to test whether an optimization preserves its intended meaning. The two findings above show why long runs on familiar dishes must be supplemented with small cases that stress limits and contention.

The scouting has therefore influenced both implementation and experimental practice. The clearest adoptions are small authoring transformations, inspectable timing, accounting, scoped diagnostics, explicit numerical contracts and tests of inherited genomes. Many larger ideas have correctly remained hypotheses. A proposal that was measured and rejected is useful research progress; it should not be counted as a shipped language feature.

**Where I think the language is still weaker.**

The largest architectural debt is the distance between the core specification and the executable language. Today, adding a new creature mechanism can require changes across the parser, checker, Rust runtime and GPU kernels. The promised library boundary—ordinary core programs defining upkeep, actions and disposal—has not been demonstrated. Faster execution makes that specialization more useful, but does not make it more general.

Support status is also harder to discover than it should be. A construct can parse, pass some checks, be omitted under partial execution, run only on the CPU, or exist only in the core draft. The compiler's `W1001` distinction is helpful. Documentation still needs a reliable backend support matrix: for example, [DISCREPANCIES.md](../crates/emerge-ref/DISCREPANCIES.md) lists catalysts as missing even though CPU support and tests exist.

Evolution itself makes apparently harmless language changes consequential. Gene order affects execution; module grouping, dormant genes and menu order can affect future offspring. The [evolutionary-semantics proposal](../proposals/evolutionary-semantics.md) identifies this well. I would make those preservation promises explicit before introducing broad optimizer rewrites or an authoring service that might be mistaken for a new mutation policy.

Finally, the ecological results should retain their scope. The [specification](../spec-v0.7.8.md) records test 9 passing in 13 of 20 seeds under its declared sustained-production criterion. That is meaningful evidence of discovery in the tested dish. It does not establish open-ended evolution, general compositional invention or reliable discovery across unrelated worlds. The recorded improvement when one of the two required pieces is preseeded is a reason to investigate accessibility under mutation, not simply to run everything longer.

**What I would do next.**

1. Fix the two GPU findings and retain small regression cases. Extend checks around contention, supported limits, empty worlds and backend feature coverage before making broader correctness claims.
2. Publish one support matrix covering parsing, checking, CPU execution, GPU execution and partial-run behavior. Correct stale status notes as part of that work.
3. Build the smallest operation report from the checked program: selection reads, settlement reads, writes, costs, phase and unsupported behavior. Let a bounded checked-edit experiment reuse it only if that improves held-out authoring tasks.
4. When core compilation is scheduled, port one existing mechanic—disposal is the candidate already proposed in [language friction](../proposals/language-friction.md)—into a template and compare it against the built-in implementation. That would provide concrete evidence that the proposed abstraction can replace engine special cases.
5. Keep larger biological and chemical extensions behind specific experimental questions and stop rules. In particular, distinguish inability to discover a combination from inability to sustain it, and distinguish structural genome proxies from measured function.

My opinion is that the project has earned confidence in its constrained experimental model and its habit of testing assumptions. The next language milestone should demonstrate that one useful mechanic can be expressed through the proposed general core while preserving the current model's resource rules, timing and evolutionary semantics.
